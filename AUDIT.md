# Pre-Submission Audit — SIH 2026 PS "Block → Panchayat Weather Downscaling"

**Audit date:** 2026-09-26 · **Commit audited:** `0f0d188` (main) · **Scope:** code, committed data, model outputs, dashboard, docs, tests, spec conformance.

**Problem statement:** Downscaling of weather forecast from Block level to Panchayat level: inferring high-resolution plots/data/information from low-resolution plots/data/information/variables for agro-meteorological advisory services.

---

## 0. Executive Summary

The engineering skeleton is good: boundaries → static covariates → residual XGBoost → rule engine → FastAPI/Leaflet dashboard, plus tests. **The scientific core, however, is not yet defensible.** A judge who reads the code will find that:

1. **The panchayat "ground truth" is generated by a formula** that uses elevation and distance to the coast (`build_feature_table.py:163-174`). The model then "learns" that same formula from those same features. The current feature table was built **before** the IMERG path existed: there is no `ground_truth_source` column, and `data/interim/panchayat_imerg.csv` has **0 rows**. So 100% of labels are synthetic.
2. **The "block forecast" is not a forecast.** It is the observed value times hard-coded, block-name-specific multipliers (VELHE/MULSHI/MAVAL ×0.78, BARAMATI/INDAPUR/DAUND ×1.18) plus Gaussian noise (`fetch_forecast.py:63-72`). The model recovers the injected bias.
3. **The "AWS stations" are Open-Meteo reanalysis grid points** (ERA5-based, roughly 9–25 km). They are not IMD or KVK instruments, but the station names suggest they are.
4. **Target leakage:** `historical_bias` is the per-panchayat mean of the target residual over the **whole dataset**, including test panchayats and test dates (`build_feature_table.py:225-227`). It is the #2 feature by importance.
5. **Headline numbers conflict:** 37.5% (LOSOCV), 82.6% (held-out) and 45.1% MAE (notebook) are all quoted, and "+37.5%" is **hard-coded** into the HTML, JS and API fallback.

➡️ **Section 11 holds the consolidated list of features to implement (F1–F34) and the model's input features.**

Items 1–4 mean that **every reported skill score measures how well XGBoost inverts our own simulator, not how well it downscales weather.** Fix Section 1 (P0) before anything else; everything else is polish.

Priority legend: **P0** = must fix before submission (a judge can disqualify on it) · **P1** = should fix (strongly affects score) · **P2** = nice to have.

## 1. P0 — Scientific Validity (Critical)

### 1.1 Synthetic, circular panchayat ground truth
- **Where:** `src/features/build_feature_table.py:160-174`
- **Problem:** `actual_p_rain = block_gt × clip(1 + 0.042·Δelev/100 − 0.002·(dist_coast−80))`. The features `elevation_mean` and `dist_to_coast_km` are model inputs, so the model is regressing a known closed-form function. The Tmax/Tmin "truth" is also a lapse-rate formula.
- **Evidence:** the committed `panchayat_features.parquet` has no `ground_truth_source` column (it is stale), `panchayat_imerg.csv` is empty (header only), and `data/raw/satellite/imerg/` is empty. The only IMERG file is a **time-averaged map** (`g4.timeAvgMap...20240601-20240930.nc`), which is not daily data and covers 2024, while the training data spans 2025-06 → 2026-08.
- **Fix:**
  - Use real, independent, spatially dense labels. Options, best first:
    1. **Maharashtra Mahavedh / Skymet AWS network**: about 2,100 revenue-circle-level AWS across Maharashtra, with dozens in Pune district. This is the best real ground truth at sub-block scale. Source it via the state agriculture department or the mahavedh portal/data request.
    2. **NASA GPM IMERG Final/Late Daily V07** (0.1°): download real daily files for the whole training period and area-weight them per panchayat polygon, not only at the centroid.
    3. **CHIRPS v2 daily (0.05°)**, which is higher resolution than IMERG and useful as a second label source.
    4. **IMD 0.25° gridded rainfall**: `src/ingest/imd_binary.py` already reads it but is **never used** in the pipeline. Wire it in as the block-level "truth"/reference.
  - Remove the orographic fallback from **training labels** entirely. If it is kept, keep it only as a clearly labelled physics baseline to compare against.
  - Rebuild the feature table, then re-run training, LOSOCV and web assets, and commit the outputs together.

### 1.2 Block forecast is simulated from observations
- **Where:** `src/ingest/fetch_forecast.py:41-78`
- **Problem:** the "forecast" = truth × block-name-specific constant + noise, so the model's skill equals the inverse of that constant. Tmax, Tmin, RH and wind are truth + noise too.
- **Fix:** use real archived forecasts at real lead times (day 1 to day 5):
  - **Open-Meteo Historical Forecast / Previous Runs API**: archived GFS, ECMWF IFS and ICON forecasts with lead-time offsets (`previous_day1..5`), free. This is the fastest real replacement.
  - **NCMRWF NCUM / IMD GFS T1534** products, if they can be accessed (matches the spec's "IMD-NCUM/GFS resampled to block").
  - Actual **IMD GKMS block-level bulletins** (PDF/Excel from the Pune DAMU/KVK). Even a few weeks is valuable as an operational validation set.
  - Aggregate the gridded forecast to **block polygons** by area-weighted mean. This mirrors the operational product.

### 1.3 "AWS" ground truth is reanalysis
- **Where:** `src/ingest/fetch_ground_truth.py:18-158, 197-202`
- **Problem:** the data comes from `archive-api.open-meteo.com` (ERA5/ERA5-Land reanalysis), labelled "Baramati KVK Agromet Station", "Pashan Agromet Observatory" and so on. It is one grid point per block, which is coarser than, or comparable to, the block itself. Some coordinates are questionable: `AWS_LAVALE` (18.54 N, 73.73 E) sits almost on Pune City/Haveli, and the "PUNE CITY" block has only 1 GP.
- **Fix:** rename these to "reanalysis reference point" in code and docs, or replace them with real station data (see 1.1). If real AWS data is obtained, use it **only for validation**, not training, and state that explicitly.

### 1.4 Silent imputation corrupts data
- **Where:** `fetch_ground_truth.py:225-229`
- **Problem:** missing rain becomes `0.0`, missing Tmax becomes `30.0`, Tmin `20.0`, RH `65.0`, wind `12.0`. Missing values turn into fake "no-rain" days and fake temperatures.
- **Fix:** keep NaN, drop or flag those rows, and report how much data is missing.

### 1.5 Target leakage via `historical_bias`
- **Where:** `build_feature_table.py:224-228`, used in `FEATURE_COLUMNS`
- **Problem:** the bias is computed on all dates and all panchayats before the train/test split, so each test panchayat's feature is the mean of its own test targets. In LOSOCV, the held-out block's bias is also computed from its own labels.
- **Fix:**
  - Compute `historical_bias` **inside each CV fold**, from **training dates only**, for training panchayats.
  - For un-gauged/held-out panchayats, the bias must come from spatial interpolation (e.g., kriging/IDW of neighbouring gauged-panchayat biases) or be dropped.
  - Add a unit test asserting that no test-set label contributes to any feature.

### 1.6 Temporal leakage and a weak split design
- **Where:** `build_feature_table.py:232-245`
- **Problem:** the random 80/20 panchayat split puts **the same dates** in train and test. Because the synthetic truth within a block is perfectly correlated in time, the test set is almost in-sample. This is why the held-out skill is 82.6%, compared with 37.5% in LOSOCV.
- **Fix:**
  - **Spatio-temporal holdout:** train on monsoon 2025 and test on monsoon 2026 (or rolling-origin), *and* hold out panchayats/stations.
  - Use `GroupKFold` by panchayat, as the spec requires (§7.2). It is not used anywhere at present.
  - Report both the temporal holdout and LOSOCV. Drop the 82.6% figure.

### 1.7 LOSOCV is actually leave-one-block-out, and its averaging is biased
- **Where:** `src/models/evaluate.py`
- **Problems:**
  - It holds out a whole block, which is fine but not what the spec means by "leave one station" (§7.3). Rename it honestly, or implement true station-level LOSO once real stations exist.
  - The mean skill is an **unweighted mean over folds**. PUNE CITY (1 GP, 153 samples) counts as much as KHED (154 GPs). Report both a pooled RMSE and a sample-weighted mean.
  - `n_folds` is an unused parameter. There are no confidence intervals: add bootstrap CIs per fold.

### 1.8 Metric definitions
- `compute_csi` returns **1.0 when there are no events** (`baseline_copy.py:21`). This inflates CSI during the dry season and at 25 mm. Return NaN instead, and report POD, FAR, frequency bias and ETS alongside CSI.
- Report metrics **by season** (monsoon vs non-monsoon), **by rain category** (IMD classes: light/moderate/heavy/very heavy), and **by lead time** (day 1–5).
- The large 25 mm CSI (0.978) is implausible for real data and is a red flag to judges.

### 1.9 Headline number is hard-coded and inconsistent
| Location | Value |
|---|---|
| `templates/index.html:46, 81, 274, 282` | "+37.5%" hard-coded |
| `static/js/dashboard.js:407` | fallback "+37.5%" |
| `app.py:62-67, 106` | fallback dict with "+37.5%" / RMSE 2.28 |
| `README.md` | 37.46% LOSOCV **and** 82.58% held-out |
| `evaluation_summary.json` | 82.58% |
| `exploratory_summary.md` | MAE improvement 45.1% (README says 34.82%) |

**Fix:** use one source of truth (a JSON file generated by the evaluation step). Have the UI and API read it with no hard-coded fallback numbers, and regenerate every figure after the P0 data fixes.

## 4. P1 — Modeling Improvements

1. **Hyperparameter tuning** over the spec grid (§7.2) with `GroupKFold`/Optuna. Currently the parameters are fixed.
2. **Stronger baselines to beat**, not just naive copy:
   - IDW/kriging of station values;
   - elevation-regression (lapse-rate / precipitation–elevation) downscaling;
   - quantile mapping / bias-corrected spatial disaggregation (BCSD);
   - the plain block forecast + climatological ratio (panchayat climatology ÷ block climatology). This is a strong and cheap classical method, and judges know it.
3. **Rain handling:** rainfall is zero-inflated and skewed.
   - Use a two-part model (occurrence classifier + amount regressor), or a Tweedie objective, or log1p residuals.
   - Currently `max(0, …)` clipping biases the output.
4. **Mass conservation option:** the area-weighted mean of panchayat values should ≈ the block value (or report the deviation). This is an important argument that the method is "downscaling", not re-forecasting.
5. **Uncertainty:** quantile regression (P10/P50/P90) or conformal intervals per GP. Advisories should be probability-aware (e.g., "70% chance > 50 mm").
6. **Explainability:** SHAP per panchayat ("why is this GP wetter than its block?"). Show it in the dashboard side panel. It makes the demo much more convincing.
7. Remove or justify `latitude`/`longitude` as raw features, since they allow memorising location. Check that `is_monsoon` being the #1 feature is not an artifact of the synthetic formula's `if is_monsoon` branch.
8. Model registry/versioning: save the feature list, training date range, metrics and a data hash alongside `residual_xgboost.json`.
9. The LightGBM branch is broken: `load()` returns a `Booster`, but `get_feature_importances` uses `feature_importances_`. Either fix it or remove it.
10. Performance: `assemble_feature_table` uses a triple nested `iterrows` loop (dates × blocks × GPs). Replace it with a vectorised merge. This is needed once multi-year daily data arrives.

## 5. P1 — Advisory Engine

1. **README rules ≠ code rules.**
   - The README says: irrigation suppression > 15 mm, heavy rain > 35 mm on slope < 3°, pest at RH > 85% and 20–28 °C, frost < 4 °C at > 800 m, wind > 30 km/h.
   - The code implements the spec thresholds: 2.5 / 50 / 35 °C & 70% / 5 °C / 40 km/h.
   - Pick one set and document it.
2. Use the downscaled panchayat features that justify downscaling: slope (waterlogging), elevation (frost), forest/water fraction. The rules currently ignore them.
3. Add missing standard agro-met advisories:
   - dry spell / rainfall deficit vs normal;
   - sowing window (onset: cumulative rain ≥ 50–75 mm over 3–7 days);
   - harvest/drying window;
   - heat wave (IMD criteria);
   - thunderstorm/lightning;
   - spray window (no rain for 6–24 h, and wind < 15 km/h);
   - fertiliser application timing.
4. Make the rules crop- and stage-specific (see 2.7). Make the rule thresholds configurable (YAML) so DAMU officers can tune them without code changes.
5. Map to the **IMD colour-coded warning** scheme (Green/Yellow/Orange/Red) as well as the Pantone palette, because IMD officers recognise it.
6. Show the choropleth colour **only** from advisory severity or from a rainfall class, not a mix. `prepare_web_assets.py:96-104` currently mixes both.

### 12.6 What could not be done, and why

* **Real AWS station validation:** IMD AWS and Maharashtra Mahavedh records are not openly downloadable.
  `src/ingest/stations.py` + `docs/stations_template.csv` accept them the moment the DAMU provides CSVs, and
  `evaluation.json → station_check` scores them automatically.
* **IMD gauge grid for 2024/2026:** imdpune.gov.in timed out and 2026 is not yet published. 2025 is used for the
  truth QA. The independent check re-runs when newer years become available.
* **GPM IMERG:** needs a NASA Earthdata login. `src/ingest/imerg.py` runs automatically when credentials are set.
* **Official IMD block bulletins as training input:** no public archive exists. The model trains on ECMWF IFS, and
  officers can upload official block values (`POST /api/downscale`).
* **Marathi GP names for search (audit 6.4):** the LGD layer carries English (romanised) GP names only.
  Machine transliteration would produce wrong names, so search is by English name or LGD code. Bulletin text,
  crop names and all advisories are fully in Marathi / Hindi.
